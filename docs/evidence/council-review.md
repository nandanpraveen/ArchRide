# Original LLM Council review

Five independent responses, followed by five anonymized peer reviews and a release synthesis. This review preceded the owner’s removal of student accounts and the November 5 simplification request. Account-specific recommendations are historical; the final guest-only scope and acceptance evidence are in [RELEASE.md](../RELEASE.md).

# Council question
What is weak or likely to fail in ArchRide's full planned/current product, and what concrete improvements and release acceptance gates are necessary to complete the project and ship a professional responsive UGA transit web app at nandanpraveen.github.io/archride using Supabase? User requests full 14-item backlog, responsive redesign, production backend, manual verification, simplicity audit and deployment. Existing uncommitted implementation must be preserved. Next 16 static export and Material UI.

## Response A
Freeze the existing working tree and produce one release checklist for all 14 board items. Several “Done” labels conflict with README and unchecked acceptance criteria. Preserve the implemented features, verify them, and update documentation against the final deployed commit.
The fastest path is three bounded workstreams: Complete missing product requirements: parking inventory and geographic bounds; restricted admin operations; active-trip revalidation and recovery. The current active-trip UI records progress, but recorded progress alone does not prove current feasibility or alert handling. Harden the static deployment: build with /archride, test every direct URL and Auth callback, and run privileged operations through authenticated Supabase Edge Functions. Deploy the exported files into the existing public user-site repository’s archride/ directory. This achieves the exact lowercase URL without publishing the private app repository or renaming it. Verify the integrated experience: one guest journey and one signed-in journey, including Saved/Class entry, denied GPS, stale transit, missed bus, account switch, deletion, and narrow-screen navigation. Test the production export rather than relying on next dev.
Do not spend implementation time inventing prediction quality. Ship the official baseline and evidence-gated model pipeline; real later-trip observations must establish improvement. Parking similarly needs an audited official inventory and explicit unknown rules, not plausible-looking pins. Keep the existing Material foundation. Improve hierarchy, spacing, map/detail composition, and touch behavior through shared tokens, avoiding a second component system. First action: run the current validation suite and capture failures before changing code.

## Response B
The project board’s “Done” labels are not release evidence. README still says planning and private features remain unfinished, while the working tree contains substantial uncommitted implementations. The first failure mode is shipping a visually polished app whose actual supported behavior nobody can identify.
Three requirements can sink this launch: Parking is an entire missing product surface. The backlog requires every TPS Athens lot, verified rules, source reconciliation, accessible alternatives, and a geographically calculated campus-plus-three-mile boundary. A rectangular campus bounding box or a handful of pins does not satisfy it. Incorrect parking permission claims have real consequences. GitHub Pages changes the architecture. Every server operation must survive static export: Auth redirects under /archride, walking requests, account deletion, trusted admin actions, and scheduled ingestion. A passing development server proves none of this. Prediction “completion” cannot be manufactured. A crowdsourced reporting UI and replay fixture do not demonstrate better predictions. Later, trip-disjoint real observations must beat the official baseline before promotion. Keep the baseline and explicitly withhold unsupported accuracy claims.
Require an acceptance ledger for all 14 items: concrete behavior, owning code, automated check, production evidence, and unresolved gap. Test the complete guest journey from building search through reachable boarding, active-trip recovery, and arrival. Separately prove two-user isolation, ownership reassignment rejection, account switching, post-deletion token behavior, and forged admin-role rejection. Spend design effort on fast, legible decisions under stale data and denied GPS. A beautiful red dashboard that makes students decipher transit internals still fails the product.

## Response C
A student should understand three things within seconds: where to go, when to leave, and what to do if the bus changes. The backlog describes those outcomes, but the Home screen still leads with “Less guessing. More getting there,” a campus badge, and several competing sections. Put “Where are you headed?” first. Make the complete recommendation the visual centerpiece: “Walk 12 minutes” or “Leave in 3 minutes for East Campus Express,” followed by boarding location and direction.
“Saved,” “Classes,” “Notifications,” and “Profile” require students to learn the app’s structure. Connect them through recognizable actions: save this journey, plan for my next class, remind me when to leave. Keep the five primary destinations stable, with secondary features reachable where they become useful.
The most dangerous confusion is false reassurance. “Live,” “on time,” “registered vehicle,” and “reminder enabled” sound definitive. Explain stale arrivals with the next useful action, distinguish parking registration from permission, and state beside reminder controls that delivery requires the app to remain open unless background delivery is actually supported.
Release acceptance should include fresh eyes, not only test authors. Give a student an unfamiliar destination and ask them to plan, identify the correct stop, miss the bus, recover, and finish without coaching. Repeat with denied location, stale data, a narrow phone, large text, and keyboard navigation. A screen passes when the student can choose the next action confidently, including when the answer is “we cannot verify a bus right now.”

## Response D
ArchRide’s strongest opportunity is becoming a student’s dependable “get me to class” tool. The backlog already connects the right pieces: campus search, complete walking/bus journeys, saved routes, classes, active-trip recovery, and reminders. The weakness is that these can ship as separate screens while the defining experience still requires too much navigation.
Make the next journey the organizing principle. Home should surface the next class or chosen destination, offer one clear planning action, then carry the same destination and deadline into trip progress, reminder delivery, and recovery. A cancelled bus should produce a reachable alternative with an updated arrival assessment, preserving the student’s intent.
The visual signature should come from campus wayfinding: clear route identities, boarding direction, readable time, and an understated red Material shell. Desktop gains a useful map/detail split; mobile gains comfortable controls and a compact journey timeline. Decorative marketing sections would weaken this utility.
Parking can create value even during a transit outage. Its checked-in, sourced inventory should remain independently usable, with explicit permit, registration, visitor-payment, and unknown conditions. The adaptive predictor offers longer-term differentiation, but the immediate asset is validated observations and reproducible evaluation, not an activated model without evidence.
Release acceptance should demonstrate one connected guest journey and one connected signed-in journey across all fourteen items. Require production walking directions, real feed freshness, working active-trip recovery, owner-isolated personal data, trusted admin operations, complete parking coverage and bounds, and account deletion that defeats old tokens. Publish tested capability limits.

## Response E
ArchRide’s product is one decision: “How do I reach this building, and when must I leave?” Every feature must support that decision. A beautiful bus map that cannot reliably produce a complete, reachable journey still fails the product.
The backlog has 14 items, but the roadmap still describes 12 and several “Done” items retain unchecked acceptance requirements. Treat board status as bookkeeping. Establish one requirement-to-evidence matrix against the final deployed commit.
Prioritize the student’s decision chain: Search → walk/bus comparison → correct boarding direction → start/resume trip → revised leave time → recovery → arrival. Then verify Saved and Classes enter that same chain with fresh data. They must never become parallel planning systems. Accounts, preferences, deletion, notifications, and admin operations must preserve ownership and consistent timing across that chain.
The architectural question is now concrete: GitHub Pages cannot execute Next.js server routes. Public static files may expose the UI; Supabase must own privileged operations, authorized walking requests, ingestion, and administration. Test direct endpoint access separately from hidden controls.
Parking is a distinct informational product with unusually expensive truth requirements. Existing source pins include repeated lots across parking, deck, and visitor layers. Deduplicate the inventory, reconcile official coverage, and show unknown eligibility where verified rules are missing. A map pin is not evidence that parking is allowed. The three-mile boundary needs an actual geographic footprint and buffer, not the planner’s current rectangular latitude/longitude check.
The crowdsourced predictor must remain evidence-gated. Code and replay tests cannot establish improvement without later, trip-disjoint observations. First action: build the release evidence matrix, then walk one real guest journey on the deployed /archride/ path.
