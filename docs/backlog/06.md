# [Week 2] Arrival estimates, deadline assessment, and reliability evaluation

## Summary

Make every arrival estimate honest and let students set an **arrive-by deadline**. Show whether a trip looks on time, tight, late, or too uncertain to assess, using evidence rather than unsupported confidence labels.

## Background

Task 2 supplies source estimates and observations; task 5 supplies complete journey candidates. Source ETAs are the initial baseline. This task owns estimate interpretation, arrive-by planning, and evaluation, not a second independent trip planner. Agree semantics with tasks 1, 4, 9, and 10.

This is a **Week 2** task, from **2026-10-18 to 2026-10-25**, with the Sunday handoff in **America/New_York**. Claim the draft in the project before starting.

## Requirements

- [ ] Create one shared arrival representation with source/calculated provenance, source time, received time, validity, and explicit missing/stale reasons. All arrival surfaces use it.
- [ ] Display absolute/local arrival time, a last-updated label, and a countdown only while valid. Define documented freshness thresholds from verified source cadence; use a controllable clock in tests.
- [ ] Implement arrive-by searches over supported departure/service data, including walking and buffers. Do not apply a current live ETA to a future time outside its valid horizon; explain unsupported future planning.
- [ ] Assess full destination arrival against the deadline and user buffer as on time, tight timing, likely late, or insufficient data. Explain the deciding factor and label all outcomes estimates.
- [ ] Collect matched prediction/observed-arrival evaluation records with route pattern and stop occurrence, deduplication, timestamps, and retention. Distinguish an observed stop arrival from a guessed proximity event.
- [ ] Produce a reproducible evaluation report with sample counts, error distribution, bias, stale/missing rate, and source coverage. Split by route/time only where sample sizes support it.
- [ ] Enable arrival windows or custom adjustments only when evaluation supports their calibration. Otherwise ship the source baseline with uncertainty text; no invented high/medium/low confidence scores.
- [ ] Update Home, route/stop details, planner, and active-trip/reminder contracts so stale or absent estimates cannot silently become zero-minute arrivals.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass. Add meaningful feature tests, including the cases below.

## Out of scope

- Training a machine-learning predictor, promising perfect arrivals, or making claims from fixture-only evaluation.
- Using live estimates as future scheduled departure times without source support.

## What we'll test

- A deadline exactly met, buffer boundary, tight/late classification, a past deadline, invalid input, and insufficient data.
- Before/after midnight, America/New_York daylight-saving changes including November 1, and different client timezones.
- Future requested trips with and without supported operating schedules; no current bus reused hours into the future.
- An estimate expires while a page stays open, an update moves backwards, negative time, source cancellation, and disconnected feeds.
- Repeated stop visits matched to the correct prediction, tiny evaluation samples, missing observations, and uncensored failure counts.
