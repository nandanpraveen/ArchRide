# [Week 3] Active trips, relevant service alerts, and missed-bus recovery

## Summary

Guide a student through an **active journey** and help them recover when the bus is missed or the plan changes. Show relevant service alerts at the point where they affect the trip.

## Background

This connects task 2’s alerts, task 4’s route/stop details, and tasks 5–6’s planning and estimates. An active session records the chosen journey and student-confirmed progress, not a continuous private location trail. Task 11 supplies labeled manual notices.

This is a **Week 3** task, from **2026-10-25 to 2026-11-01**, with the Sunday handoff in **America/New_York**. Claim the draft in the project before starting.

## Requirements

- [ ] Let the student start, resume, and end a trip with walk-to-stop, wait/board, ride, exit, and final-walk steps. Show the route direction, boarding and exit stops, timing, freshness, and destination.
- [ ] Persist an owner-only signed-in active session and a limited local guest session with expiry. Reopening the app revalidates the trip against current data.
- [ ] Aggregate active agency alerts and separately labeled manual notices. Filter by affected route/stop/time, expose details and validity, and integrate alerts into Home, map details, Plan, and active trips.
- [ ] When an estimate changes materially, a valid source cancellation occurs, or a user confirms a missed bus, recalculate feasible alternatives: next bus, another boarding stop, another supported direct route, or walking.
- [ ] Explain the tradeoff and revised deadline assessment. Require a student confirmation when a missed bus or boarding cannot be determined reliably; a disappearing vehicle is not a closed route.
- [ ] Avoid repeated recovery prompts and preserve the original destination and preferences. Dismissed/expired alerts stop affecting the current recommendation appropriately.
- [ ] Provide explicit arrived, end/cancel, stale/no-data, reroute unavailable, offline, and destination-changed states. Wire trip events into task 10’s notification/reminder contract.
- [ ] Use accessible Material detail panels, clear progress text, keyboard actions, and a safe exit from every stage.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` pass. Add meaningful feature tests, including the cases below.

## Out of scope

- Multi-bus transfers, automatic boarding claims from weak GPS, or route-closure inference from missing vehicles.
- Continuous user location storage or unsupported agency notices.

## What we'll test

- Start/resume/end as guest and user; refresh mid-trip, completed-trip expiry, sign-out, and account switching.
- Bus missed, student still boarding, bus temporarily missing, explicit cancellation, detour, alert expiry, and multiple affected routes.
- Every offered recovery is reachable and direction-correct; none uses an already departed bus.
- A faster walk, next bus, alternate stop, no alternative, stale feed, and deadline status changing after recovery.
- Duplicated/reordered updates, dismissed notices, clock changes, keyboard trip controls, and labelled agency versus manual alerts.
